# Model card — `bge-small-duediligence`

A domain-adapted bi-encoder for retrieval over SEC EDGAR filings, fine-tuned
from `BAAI/bge-small-en-v1.5` on the corpus described below.

**The weights are not published.** They stay local and gitignored ([#25](https://github.com/Dayallenr/RAG/issues/25)).
This card is the artifact: it exists so a reader can judge the work without
downloading anything and without running anything. What that decision costs the
claim is stated in [What shipping no weights costs](#what-shipping-no-weights-costs),
not left for a reader to notice.

Every number here comes from a report file in `results/`, named at the point of
use.

---

## At a glance

| | |
|---|---|
| Base model | `BAAI/bge-small-en-v1.5` |
| Architecture | Transformer → Pooling → Normalize, 384-dimensional, `max_seq_length` 512 |
| Objective | `MultipleNegativesRankingLoss` with one explicit mined hard negative per row |
| Training data | 12,758 triplets from 4,776 synthetic queries over the project's own corpus |
| Hardware | one RTX 5070 (CUDA, fp16), 121 seconds |
| Headline result | dense recall@10 **0.367 → 0.600** on the held-out test split (**+0.233**) |
| Result through the shipped pipeline | **+0.000 on every metric** — see [The delta](#the-delta) |
| Provenance | digest manifest present; 9 of 10 files match, `modules.json` does not — see [Provenance](#provenance-what-ties-these-weights-to-that-run) |

Both headline numbers are load-bearing and **travel together**. Quoting +0.233
alone describes a configuration nobody runs; quoting +0.000 alone calls a
working model a failure.

---

## Intended use

Retrieving passages from a corpus of US regional-bank SEC filings — 10-K, 10-Q
and 8-K narrative text, serialized financial tables, and generated chart
descriptions — in response to due-diligence questions. It is the dense half of
a hybrid retriever; the lexical half is BM25 over the same index, and the
project's shipped configuration fuses the two with RRF and reranks the result
with a cross-encoder.

It is **not** a general-purpose sentence encoder. It was adapted to one
five-company corpus of one document genre in one regulatory register, and every
number below was measured on questions written against that corpus. Nothing
here supports a claim about its behaviour on other domains.

It is not a generation model, does not judge relevance, and produces no
citations. It ranks passages.

## Out-of-scope and known limitations

- **Corpus-specific.** Five companies (COLB, UMPQ, GBCI, WSBC, SSB), 502
  filings. Financial language outside US bank-holding-company disclosure is
  out of distribution.
- **The gain does not reach the shipped pipeline.** This is measured, not
  suspected, and the arithmetic is in [The delta](#the-delta). Deploying this
  model without also changing the fusion settings is a measured no-op for
  users.
- **Weakest where dense retrieval is structurally weak.** Serialized tables are
  numeric soup for a 384-dimensional semantic embedding. Fine-tuning moved that
  a long way (see the chunk-type table) without changing the underlying
  mismatch.
- **Sequence length is a real ceiling.** Mined positives run past the 512-token
  window on 6.8% of rows; those are truncated, in training and at serving alike.
- **One epoch, one run, one seed.** No sweep, no repeat, no confidence
  interval. The delta reproduces across three splits of the same eval set,
  which is consistency, not statistical significance.
- **Trained on synthetic queries** whose lexical bias is described below, and
  evaluated on human questions carrying a related bias. Both are stated in
  [Confounds](#confounds-the-number-is-a-floor-not-an-estimate).

## Training data

### Where the queries came from

The project has 101 hand-written evaluation questions — far too few to train
on, and, more to the point, they are the exact questions the headline retrieval
numbers are scored against. Training on them would make the reported
improvement a measurement of memorisation.

So training queries were generated from the corpus instead, in the established
doc2query/InPars style: show a model a passage, ask what questions it answers,
keep the pairs. **4,776 queries** (`data/training/synthetic_queries.jsonl`),
generated by `qwen3:8b` served locally through Ollama — recorded per row as
`generated_by`, so the provenance is in the data and not only in this sentence.

Source passages were drawn by a **stratified sample across (company, chunk
type)** rather than uniformly. A uniform sample would be dominated by
paragraphs, which outnumber every other chunk type by an order of magnitude,
and would have starved exactly the table and section chunks where the gap was
largest.

### The contamination guard

Enforced in `duediligence/train/synthetic.py` and asserted by tests in
`tests/test_synthetic.py`, because "we remembered not to train on the test set"
is not a property anyone can verify later, whereas a failing test is.

Two checks, at different stages:

1. **By chunk.** Every chunk that any evaluation question is labelled against is
   excluded from query generation outright.
2. **By question.** Any generated query whose normalised token set is too close
   to an evaluation question is dropped.

Both refuse to run if `data/eval_set.jsonl` is missing, rather than silently
treating an absent eval set as "nothing to exclude" — which would produce
contaminated training data that looks clean.

### Hard-negative mining

Contrastive fine-tuning learns from what it must push apart. Random negatives
are trivially separable — a question about one bank's deposits against a
passage on another bank's board committees teaches close to nothing — so
negatives are mined from the retriever's own confusions.

For each synthetic query, the **live hybrid retriever** (RRF over BM25 and the
off-the-shelf dense model, candidate depth 20) is run over the full 38,483-chunk
index. The top hit is skipped, and up to **3 negatives per query** are selected
from what remains. Yield: **12,758 training triplets** and **1,429 validation
triplets** (`data/training/train.jsonl`, `val.jsonl`, both tracked in git).

Two selection details that were bugs first:

- **Company names are normalised before mining.** The generation prompt passed
  the ticker as metadata, so the model wrote questions about "Colb" and "Wsbc".
  No real user asks about "Colb", and training on those spends model capacity
  on a token that never appears in a genuine query.
- **Negatives are excluded by normalised text, not only by chunk id.** The same
  boilerplate paragraph recurs across filings under different ids, so excluding
  the positive by id alone let its byte-identical twin back in as a "hard
  negative" — 1,069 of 14,292 mined rows, across 505 queries, asking the loss to
  score one string as both positive and negative for the same anchor. That is
  not a hard example, it is an unsatisfiable one, and nothing about it raises an
  error.

### The split discipline

**Split by query, never by row.** One query yields several triplets. Letting
those land on both sides of the train/validation boundary would leak validation
into training and make the eval loss curve meaningless — it would be measuring
recall of rows the model had already seen under a different negative.

**The 101 human questions are held out entirely.** None of them, and no chunk
any of them is labelled against, appears anywhere in training. They are further
split into a frozen **71-question development** and **30-question test** split
(`scripts/assign_eval_splits.py`), and the headline delta below is quoted on the
test split — the only one no tuning decision has touched, since both the fusion
weight and the rerank depth were swept against dev.

## Training procedure

One run, on the author's own RTX 5070. It does not fit on the Mac that serves
the index: measured there, batch 32 and batch 16 both OOM against a ~9 GiB
ceiling, and batch 8 swaps at ~710 s/step, which is ~13 days for one epoch.
That measurement is why [ADR 0005](adr/0005-fine-tune-the-bi-encoder.md) put
training on a separate machine.

From `results/training/report.json`:

| | |
|---|---|
| Base model | `BAAI/bge-small-en-v1.5` |
| Loss | `MultipleNegativesRankingLoss` (in-batch negatives + 1 explicit mined negative) |
| Epochs | 1 (399 optimizer steps) |
| Batch size | 32 |
| Learning rate | 2e-5, warmup ratio 0.1 |
| Precision | fp16 |
| Gradient checkpointing | off — wired through the script, never needed on this hardware |
| Device | CUDA (RTX 5070) |
| Wall-clock | **121 seconds** |
| Train triplets / validation triplets | 12,758 / 1,429 |

Loss curve, both series falling monotonically with **eval below train at every
checkpoint** — the shape of a model that has not begun to overfit, which is
what one epoch on 12,758 rows should look like:

| step | train loss | eval loss |
|---|---|---|
| 25 | 1.761 | |
| 100 | 0.751 | 0.652 |
| 200 | 0.649 | 0.567 |
| 300 | 0.570 | 0.529 |
| 375 / 399 | **0.538** | **0.520** |

A falling contrastive loss is evidence the objective was optimised. It is not
evidence of retrieval improvement — that is the next section, measured
separately on data the model never saw.

## The delta

Measured by a **four-run matrix** — off-the-shelf and fine-tuned, each with and
without the cross-encoder — because those two pairs answer different questions
and only one of them describes the served system
(`scripts/run_finetune_delta.py`, `results/finetune_delta/report.json`).

The two arms provably queried different indexes, each holding its own model's
vectors, and BM25 is identical across arms by construction — all three checked
in the report's `consistency` block rather than assumed.

### Held-out test split, 30 questions, all human-verified

| retriever | recall@1 | recall@10 | MRR | nDCG@10 |
|---|---|---|---|---|
| dense, base | 0.267 | 0.367 | 0.303 | 0.319 |
| dense, **fine-tuned** | 0.300 | **0.600** | 0.426 | 0.466 |
| **Δ dense** | **+0.033** | **+0.233** | **+0.123** | **+0.147** |
| hybrid + cross-encoder rerank, base | 0.300 | 0.667 | 0.412 | 0.468 |
| hybrid + cross-encoder rerank, **fine-tuned** | 0.300 | 0.667 | 0.412 | 0.468 |
| **Δ shipped pipeline** | **+0.000** | **+0.000** | **+0.000** | **+0.000** |

The dense gain is large and it lands where the gap was: the fine-tuned dense
retriever reaches **parity with BM25** on this split (0.600 vs 0.600), closing
the roughly-2x deficit that motivated the run at all. It reproduces across
splits — **+0.233** on test, **+0.232** on dev (n=71), **+0.233** on all 101 —
and it is concentrated on the chunk types dense retrieval handled worst. Dense
recall@10 by chunk type, over all 101 questions:

| chunk type | n | base | fine-tuned | Δ |
|---|---|---|---|---|
| table | 40 | 0.200 | **0.550** | +0.350 |
| section | 20 | 0.350 | **0.650** | +0.300 |
| chart description | 5 | 0.600 | **1.000** | +0.400 |
| paragraph | 35 | 0.414 | 0.457 | +0.043 |
| document | 1 | 0.000 | 0.000 | +0.000 |

### And the shipped pipeline's number does not move at all

Not approximately. The cross-encoder returned **byte-identical result lists on
all 101 questions** in both arms. The cause is fusion arithmetic, and
`scripts/verify_rerank_pool.py` checks it against the live index rather than
deriving it on paper.

RRF scores a document `weight / (60 + rank)`. A document only dense retrieval
finds scores at best `0.25 / 61`, while BM25's document at candidate depth `c`
scores `1 / (60 + c)` — so a dense-only document cannot enter the fused pool
until `c > 184`. The pipeline runs at **50**. Measured on the test split
(`results/finetune_delta/rerank_pool.json`): the fused pool **equals BM25's
candidate set on 30/30** questions in both arms, identical as sets 30/30,
identical in order **0/30**.

The fine-tuned embeddings reorder the pool the reranker is handed and never
change its membership — and reordering is precisely what a cross-encoder
discards. **A null reranked delta under this configuration is a property of the
fusion settings, not evidence about this model.**

It reproduces at the serving layer too, through the API rather than the eval
harness (`results/serving/profile_check.json`): with reranking off at candidate
depth 50, the two profiles returned the **same 50 documents in a different
order** on all three probe queries — membership identical, order not.

Realising this gain in the served pipeline is therefore a **fusion** change —
dense weight, candidate depth past 184, or reranking a dense-sourced pool — not
more training. No ticket has been opened for it yet.

## Confounds: the number is a floor, not an estimate

Carried from `results/finetune_delta/report.json`'s own `confounds` block, so
this card and the report cannot drift apart. All three apply **equally to both
arms**, so the delta is more robust to them than the absolute levels are.

1. **Relevance labels are incomplete.** They average **1.02 chunks per
   question**, drawn from a stratified candidate pool rather than exhaustive
   judgments over all 38,483 chunks. A retriever that returns an unlabelled
   chunk which genuinely answers the question is scored as missing it. Every
   recall figure here is a floor.
2. **The questions were drafted by reading the passages they are labelled
   against**, so they reuse those passages' vocabulary — which structurally
   favours lexical matching over semantic matching. The dense arm is measured
   under that handicap in both arms.
3. **The fusion weight of 0.25 was swept against the development split**, so
   hybrid figures on dev carry that optimisation. This is why the headline is
   quoted on test.

A fourth, specific to this card: the synthetic training queries were generated
by reading their source passages and inherit the same lexical-overlap bias. That
does not invalidate a delta measured on the held-out human set, but it does mean
the training distribution is not a neutral sample of how a real user asks.

## Provenance: what ties these weights to that run

`results/training/report.json` records losses and hyperparameters but **no
checkpoint identity** — not a path, not a hash. The link is
`results/training/checkpoint.json`, a SHA-256 digest manifest written on the
training machine by `scripts/transfer_checkpoint.py manifest` and committed, so
it travels by git while the weights travel by another channel. A manifest
shipped alongside the weights would be signed by the same corruption it exists
to catch.

**The manifest is present, and it does not fully verify.** Run here against the
weights on the serving machine:

```
$ python scripts/transfer_checkpoint.py verify
models/bge-small-duediligence does not match results/training/checkpoint.json:
  digest mismatch: modules.json (expected 5861cc45c276…, got a0f5ee40975a…)
```

Exit 1. File by file:

| file | bytes | matches the manifest |
|---|---|---|
| `model.safetensors` | 133,462,128 | **yes** |
| `config.json`, `tokenizer.json`, `tokenizer_config.json`, `sentence_bert_config.json`, `config_sentence_transformers.json`, `README.md` | — | yes |
| `1_Pooling/config.json`, `2_Normalize/config.json` | 93, 100 | yes |
| `modules.json` | 410 | **no** |

So **the weights themselves are cryptographically tied to the 2026-08-18
training run** — all 133 MB of `model.safetensors`, plus the tokenizer, the
architecture config, and both nested module configs. The single mismatch is
`modules.json`, a 410-byte list naming the three pipeline modules. It contains
no weights and no hyperparameters.

What is known about that one file, as measurement rather than inference:

- The checkpoint was written by **sentence-transformers 6.0.0** (torch
  2.11.0+cu128, transformers 5.15.0) — recorded in
  `config_sentence_transformers.json`, which *does* match the manifest. The
  serving machine runs sentence-transformers **5.7.0**, and loading the
  checkpoint here emits a version-mismatch warning.
- `modules.json` alone carries a distinct modification time on this disk
  (15:32, against 22:29 for the files that verify), so it was rewritten locally
  after the checkpoint arrived rather than in transit.

The account most consistent with that evidence is that the 6.0.0-format module
list was rewritten by hand into the 5.x form this machine can load. It is
labelled an account, not a conclusion, because nobody recorded doing it.

**What this supports and what it does not.** The delta above is an attributable
measurement of the trained weights: the file carrying every parameter matches
the manifest byte for byte. What is *not* clean is the checkpoint directory as a
whole — `verify` exits 1, and this card does not describe a failing check as a
passing one. Restoring a clean verify means re-running
`transfer_checkpoint.py manifest` on the training machine against the
checkpoint it still holds, or recording the local edit deliberately.

This is also why `results/finetune_delta/report.json` reports
`weights_traceable_to_this_run: false`. That field is set from an **actual digest
comparison**, not from the manifest's presence: a manifest is a claim about
specific bytes, and treating its existence as proof would make a corrupted or
substituted checkpoint read as verified — worse than reporting no manifest at
all, because it would look checked.

Independent of the manifest, the checkpoint on this machine was measured to be a
real fine-tune of the base model rather than a copy of it: 384-dimensional,
L2-normalized output, `max_seq_length` 512, `Transformer → Pooling → Normalize`,
and cosine **0.68** against `BAAI/bge-small-en-v1.5` on a probe query — moved,
and not to a degenerate space. Each index was separately confirmed to hold its
own model's vectors (cosine 1.000000 against its own model, 0.857 against the
other's, `results/index/report.json`), which is what rules out the delta being
an artifact of one arm querying the wrong index.

## What shipping no weights costs

There is no downloadable checkpoint. The fine-tune claim therefore rests on:

- the training script (`scripts/finetune_biencoder.py`) and the training module
  it drives (`duediligence/train/`);
- the tracked training data — all 12,758 train and 1,429 validation triplets are
  in git, deliberately, because an untracked input to a reported number is
  exactly the failure this project's rules exist to prevent;
- `results/training/report.json`, `results/finetune_delta/report.json` and the
  four run reports beneath it;
- the digest manifest, with the one caveat above.

That is the same evidence standard as every other claim in this repository —
but it is **weaker than a downloadable checkpoint would have been**. A reader
cannot re-run the evaluation against these weights, and cannot confirm that the
indexed model is the one this card describes except through the digests.

It is partly compensated by third-party hosting: every report above is also
logged to a **public** Weights & Biases project that this repository cannot
edit, and `scripts/verify_wandb_runs.py` diffs every hosted metric against
`results/` using **no credentials** — a key in that request would make a private
project look public, which is the one way the check could certify something
false.

## Reproducing this

Requires the corpus indexed locally (`docker compose -f
docker/docker-compose.yml up -d`, then `python scripts/build_index.py`) and, for
the training step, a CUDA machine.

```bash
# 1. synthetic queries (local Ollama, no OpenSearch needed)
python scripts/generate_synthetic_queries.py

# 2. hard negatives — needs the live index
python scripts/mine_hard_negatives.py

# 3. train (CUDA; ~121 s on an RTX 5070) — writes results/training/report.json
python scripts/finetune_biencoder.py

# 4. tie the weights to the run, on the training machine, and commit the result
python scripts/transfer_checkpoint.py manifest

# 5. where the weights are: check them against that manifest
python scripts/transfer_checkpoint.py verify

# 6. index the fine-tuned model — the baseline index is untouched
DUEDILIGENCE_CONFIG_PROFILE=finetuned python scripts/build_index.py --recreate

# 7. the four-run matrix and the comparison
python scripts/run_finetune_delta.py
python scripts/verify_rerank_pool.py
```
